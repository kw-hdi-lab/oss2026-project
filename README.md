# 팀 프로젝트 주제 정하기

주제는 팀이 자유롭게 정합니다. 단, 수업에서 다루는 내용(화면, 테스트, 서버, LLM 호출, 컨테이너, 배포)을 모두 프로젝트에 적용할 수 있어야 하므로 아래 조건을 지켜야 합니다.

주제와 기능은 프로젝트를 진행하면서 바꿀 수 있습니다. 처음부터 완성된 계획을 세울 필요는 없습니다. 만들 수 있을지 확신이 없다는 이유로 주제를 작게 잡지 마세요. 진행하다가 어려운 부분이 생기거나 더 나은 방향이 보이면 그때 조정하면 됩니다.

## 1. 아이디어 점검

주제를 정할 때 아래 네 질문에 답할 수 있어야 합니다.

### 누가, 언제, 무엇 때문에 불편한가요?

대상을 구체적으로 적습니다. "바쁜 직장인", "모든 대학생"은 너무 넓습니다. "수업이 밤 9시에 끝나는 통학생이 막차 시간을 매번 따로 찾아본다" 정도로 적어 주세요.

팀원 본인이나 주변 사람이 대상이면 좋습니다. 그런 사람 두세 명에게 실제로 물어보고 들은 내용을 한 줄씩 적으면 더 좋습니다.

### 지금은 어떻게 해결하고 있나요?

지금 쓰는 방법(엑셀, 카톡방, 메모장, 기존 앱 등)을 적고, 그 방법으로 부족한 점을 적습니다. 부족한 점이 없으면 주제를 다시 고르세요.

### ChatGPT에게 직접 물어보면 되지 않나요?

"AI가 ~를 해 준다"로 설명되는 아이디어는 대부분 ChatGPT로 대신할 수 있습니다. ChatGPT로 대신할 수 없는 이유를 적어야 합니다. 다음 중 하나 이상에 해당하면 됩니다.

- 사용할수록 데이터가 쌓인다 (기록, 이력)
- 여러 사람이 같은 데이터를 보고 수정한다 (투표, 공유 목록)
- 외부의 실시간 데이터를 가져온다 (버스 도착 정보, 날씨, 공공데이터)
- 같은 입력에 항상 같은 결과가 나와야 한다 (계산, 판정)
- 매번 질문을 입력하는 것보다 화면에서 고르는 것이 빠르다

예를 들어 "AI 여행 플래너: 여행지와 날짜를 넣으면 일정을 짜 준다"는 ChatGPT에 같은 문장을 넣으면 같은 결과가 나옵니다. 반면 "동아리 MT 장소 정하기"는 다음 이유로 ChatGPT로 대신할 수 없습니다.

#### 여러 사람이 함께 쓴다

ChatGPT로 하면 한 사람이 후보를 물어보고, 그 결과를 카톡방에 옮기고, 투표를 받아 손으로 셉니다. 앱에서는 회원 20명이 각자 링크를 열어 투표하고, 서버가 표를 저장하고, 모두가 같은 집계 결과를 바로 봅니다. 여러 사람이 같은 데이터를 공유하는 일은 한 사람과 대화하는 ChatGPT가 할 수 없습니다.

#### 데이터가 쌓인다

ChatGPT는 작년 MT 장소에서 실제로 1인당 얼마가 들었는지, 회원들이 어떤 후기를 남겼는지 모릅니다. 매년 누군가 그 내용을 다시 찾아 붙여 넣어야 합니다. 앱은 지난 MT의 장소, 실제 비용, 후기를 저장해 두고, 다음 해에 같은 장소가 후보에 오르면 함께 보여 줍니다.

#### 같은 조건이면 같은 결과가 나온다

ChatGPT에 같은 조건을 두 번 물으면 다른 후보가 나올 수 있고, 예산을 넘는 곳이 섞여 나오기도 합니다. 앱은 "수용 인원이 참가 인원 이상, 1인당 비용이 예산 이하, 학교에서 이동 시간 2시간 이내"를 코드로 계산하므로 같은 입력에 항상 같은 후보가 나옵니다. 이 계산이 맞는지는 테스트로 확인할 수 있습니다.

#### LLM은 일부에만 쓴다

팀 프로젝트에는 LLM 호출이 하나 이상 들어가야 합니다(2장 "LLM 호출" 참고). 이 앱에서는 후보를 고르는 것은 위의 계산 규칙이 하고, LLM은 저장된 정보(시설, 후기)를 바탕으로 후보마다 한 줄 소개를 쓰는 데만 씁니다. LLM 호출이 실패해도 후보 목록과 투표는 그대로 동작합니다.

### 가장 먼저 완성할 기능 하나는 무엇인가요?

앱에서 가장 중요한 기능 하나를 정합니다. 사용자가 앱을 열고, 값을 입력하고, 결과를 확인하기까지의 과정이 이 기능 하나로 완결되어야 합니다. 이 기능을 먼저 완성하고, 다른 기능은 그다음에 추가합니다. 여러 기능을 조금씩 만들어 두는 것보다 기능 하나가 제대로 동작하는 것이 중요합니다.

## 2. 주제가 갖춰야 할 조건

### 화면

사용자가 값을 입력하거나 선택하고, 그 결과를 확인하는 화면이 있어야 합니다. 정보만 보여 주는 페이지는 안 됩니다.

### 계산 규칙

입력을 받아 결과를 계산하는 규칙이 있어야 합니다. 조건에 맞는 항목 골라내기, 점수나 순위 매기기, 입력값 검사, 합계와 통계 같은 것입니다. 화면 없이도 "이 입력이면 이 결과"를 확인할 수 있어야 하고, 테스트를 다섯 개 이상 쓸 수 있을 만큼은 있어야 합니다.

### 서버

서버가 맡을 일이 있어야 합니다. 데이터를 저장하거나(메모리나 JSON 파일로 충분합니다), 키가 필요한 외부 API를 호출하는 것입니다. 엔드포인트(endpoint)는 두 개 이상 둡니다.

### LLM 호출

서버 코드에서 LLM API를 호출하고, 그 응답을 앱의 기능에 쓰는 부분이 하나 있어야 합니다. 사람이 채팅창에 질문하는 것과 다릅니다. 앱의 데이터를 LLM에 보내고, 응답을 화면에 표시하거나 저장합니다. 예를 들면 다음과 같습니다.

- 사용자가 쓴 후기를 긍정과 부정으로 분류해 저장한다
- 모인 기록을 세 줄로 요약해 보여 준다
- "다음 주 저녁, 3만 원 이하" 같은 문장을 검색 조건으로 바꾼다

LLM 호출이 실패해도 나머지 기능은 동작해야 합니다.

### 규모

GPU, 대형 모델, 대용량 파일이 필요 없어야 하고, 메모리 512MB 정도에서 실행되어야 합니다. 수업에서 안내하는 무료 플랜으로 배포할 수 있는 수준이면 됩니다. 실제 배포는 다른 곳에 해도 됩니다.

### 공개

저장소와 배포된 앱은 누구나 볼 수 있습니다. 공개해도 되는 데이터만 씁니다.

### 세 사람의 몫

기능을 셋으로 나눌 수 있어야 합니다. 팀원마다 화면, 계산 규칙, 서버 API를 하나 이상씩 맡고, 최종 발표에서 각자 자기 부분을 직접 시연합니다.

## 3. 기술

- 프론트엔드는 HTML/CSS/JavaScript로 만듭니다. 수업도 이 방식으로 진행합니다. 팀원 모두가 React, Vue, Svelte 같은 프레임워크를 이미 다룰 수 있다면, Vite로 만드는 프레임워크를 써도 됩니다. 이 프로젝트를 위해 프레임워크를 새로 배울 필요는 없습니다.
- 백엔드는 Express로 직접 만듭니다.
- Next.js, Nuxt, SvelteKit, Remix처럼 서버까지 포함한 프레임워크는 쓰지 않습니다. 브라우저와 서버가 HTTP로 통신하는 부분을 직접 만드는 것이 이 프로젝트의 목적인데, 이 프레임워크들은 그 부분을 자체적으로 처리합니다. 같은 이유로 Vercel처럼 배포 과정을 자동으로 처리하는 서비스도 쓰지 않습니다.
- 계산 규칙은 화면 코드와 다른 파일에 함수로 둡니다. 그래야 화면 없이 테스트할 수 있습니다.
- 팀원 세 명 모두가 서로의 코드를 읽고 리뷰할 수 있어야 합니다.
- JavaScript를 권장합니다. TypeScript는 팀이 정합니다.

## 4. 제한 사항

- 회원가입, 로그인, 결제 (보안 처리를 수업에서 다루지 않습니다)
- 실제 개인정보 수집 (저장소와 앱이 공개됩니다)
- 공식 API가 없는 사이트의 화면을 긁어 와서(크롤링) 동작하는 기능. 외부 데이터는 공식 API나 공개 데이터 파일(공공데이터포털 CSV 등)로 가져옵니다.
- 유료 API가 있어야만 동작하는 기능

브라우저 게임도 위 조건을 모두 만족하면 됩니다.

실시간 통신(WebSocket 등)은 수업에서 다루지 않습니다. 구현하려면 팀이 직접 익혀야 하고, 주요 기능은 실시간 통신 없이 Express API만으로 동작해야 합니다. 실시간 통신은 그 위에 추가하는 기능으로만 씁니다.
